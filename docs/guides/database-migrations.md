# Руководство по миграциям базы данных

## [C] Контекст

Backend проекта использует Alembic для версионирования схемы PostgreSQL. Файлы ревизий находятся в `backend/migrations/versions/`, модели SQLAlchemy — в `backend/src/uptime/infrastructure/models.py`, а `backend/migrations/env.py` загружает их metadata и подключается к базе по `DATABASE_URL`. Контейнер backend при запуске выполняет `alembic upgrade head`.

Следуйте этому руководству при изменении моделей или схемы базы, а также при проверке уже подготовленной миграции. Команды Alembic запускаются из `backend/`. Для команд, которым требуется реальная база, сначала запустите PostgreSQL из корня репозитория: `docker compose up -d db`.

Перед запуском проверьте доступность базы именно из текущей среды. `DATABASE_URL` из `docker-compose.yml` использует имя хоста `db` и работает внутри сети Compose; при запуске Alembic непосредственно на компьютере задайте URL доступной ему PostgreSQL. Сервис `db` в текущем compose-файле не публикует порт на хост.

## [O] Результат / Цель

Изменения схемы должны быть представлены новой ревизией Alembic, корректно применяться к актуальной и пустой базе, соответствовать моделям и иметь безопасный `downgrade()` там, где откат возможен.

## [S] Границы

- Не редактируйте уже применённые и опубликованные ревизии. Создайте следующую ревизию.
- Не считайте автосгенерированную миграцию готовой без ручной проверки.
- Не запускайте `downgrade` на общей или production базе без явной задачи и согласованного плана восстановления данных.
- Не удаляйте данные и не ослабляйте ограничения молча. Изменения, теряющие данные, требуют явно описанной стратегии.
- Держите миграцию, модели и связанные изменения приложения согласованными.

## [T] Порядок работы и проверки

### 1. Изучить исходное состояние

Из каталога `backend/` проверьте историю и текущие вершины графа ревизий:

```powershell
alembic current
alembic history --verbose
alembic heads
```

Убедитесь, что история понятна, а ожидаемая вершина одна. Несколько heads означают разветвление графа: выясните причину и при необходимости подготовьте merge revision, не выбирайте head наугад. Если команда `current` не может подключиться, проверьте, что база запущена и `DATABASE_URL` указывает на неё.

### 2. Обновить модель данных

Внесите согласованные изменения в SQLAlchemy модели (`src/uptime/infrastructure/models.py`) и код приложения. Продумайте типы и nullability столбцов, defaults, ограничения, индексы и внешние ключи. Для существующих строк проверьте, что новые обязательные поля можно заполнить безопасно; при необходимости используйте несколько этапов миграции вместо немедленного `NOT NULL`.

### 3. Создать новую ревизию

Сгенерируйте заготовку автодетектом изменений:

```powershell
alembic revision --autogenerate -m "describe schema change"
```

Команда создаёт новый файл в `migrations/versions/`. Она подключается к базе для сравнения metadata со схемой. Запускайте её с `DATABASE_URL`, доступным из среды, где вызван Alembic; одного запуска `docker compose up -d db` недостаточно для доступа с компьютера, пока порт базы не опубликован.

### 4. Проверить и при необходимости исправить ревизию

Прочитайте весь новый файл и сравните `upgrade()` с требуемым изменением. Alembic autogenerate не распознаёт все изменения и не гарантирует правильную миграцию. Вручную подтвердите:

- корректны `revision` и `down_revision`, новая ревизия продолжает ожидаемую ветку;
- добавлены все нужные таблицы, столбцы, индексы, ограничения и внешние ключи;
- типы, длины, nullability и имена ограничений соответствуют моделям;
- переименование не стало незаметной парой «удалить старое / создать новое» с потерей данных;
- значения для новых обязательных полей заполняются до установки `NOT NULL`;
- порядок операций учитывает зависимости и существующие данные;
- `downgrade()` отменяет операции в обратном порядке и не оставляет частично изменённую схему.

Если миграция должна преобразовать данные, добавьте явные операции преобразования и предусмотрите, как они ведут себя при повторном развёртывании. Не полагайтесь на Python default модели: серверный default для существующей базы должен присутствовать в самой миграции, если он необходим.

### 5. Применить миграцию и проверить базу

Сначала примените все ревизии до актуальной вершины:

```powershell
alembic upgrade head
alembic current
alembic check
```

Проверьте, что `upgrade` завершился успешно, `current` показывает ожидаемую ревизию, а `alembic check` сообщает об отсутствии незаписанных различий между metadata и схемой. Если `alembic check` недоступен в установленной версии, сравните результат `alembic revision --autogenerate` на чистом состоянии; он не должен предлагать неожиданных операций.

Для локальной базы также проверьте запуск приложения: из корня выполните `docker compose up --build -d`, затем `docker compose ps` и `docker compose logs backend`. Backend должен оставаться запущенным без ошибки миграции; compose пока не задаёт healthcheck для backend. При необходимости проверьте API health endpoint, если он определён в приложении. Не считайте только успешный старт контейнера доказательством корректности данных.

### 6. Проверить установку с нуля

Убедитесь, что последовательность ревизий создаёт схему на пустой базе, а не только обновляет вашу уже изменённую локальную базу. Используйте отдельную временную базу PostgreSQL или изолированный тестовый compose-проект и примените:

```powershell
alembic upgrade head
alembic current
```

Затем проверьте, что приложение стартует на этой схеме и нужные таблицы, ограничения и индексы существуют. Не удаляйте и не пересоздавайте общий Docker volume ради этой проверки: в нём могут находиться нужные данные.

### 7. Проверить откат, если он безопасен

Только на временной базе без ценных данных проверьте новый шаг отката: сначала примените миграцию, затем выполните `alembic downgrade -1`, проверьте ожидаемое предыдущее состояние и снова выполните `alembic upgrade head`. Для ревизии, которая теряет или необратимо преобразует данные, явно укажите ограничение отката и не имитируйте безопасный `downgrade()`.

### 8. Завершить изменение

Повторно проверьте граф (`alembic heads` должен отражать ожидаемую вершину), итоговый diff моделей и миграции, а также связанные backend тесты. Убедитесь, что новая ревизия включена в изменения. В описании PR укажите, как миграция проверялась, есть ли преобразование или риск потери данных и требуется ли действие при развёртывании.

Готово, когда:

- новая схема описана отдельной ревизией и ревизия проверена вручную;
- `alembic upgrade head` проходит на обновляемой и чистой базе;
- `alembic current` показывает ожидаемую ревизию;
- `alembic check` не находит пропущенных изменений (или расхождения проверены вручную);
- backend запускается с обновлённой схемой, связанные тесты проходят;
- поведение отката и возможные потери данных документированы.
